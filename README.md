# BiliMusic · 用 B 站当音乐源

把哔哩哔哩当作 LX Music 播放源的自定义音源实现。

- **LX Music 自定义音源**（`lx_bili_source.js`）：在 LX 里正常搜索，播放时把取流换成 B 站视频音轨。

> 仅供个人学习与技术研究。所有音视频版权归原作者与哔哩哔哩所有，请勿用于传播或商业用途。

## 一、安装与使用

1. 下载 [`lx_bili_source.js`](./lx_bili_source.js)
2. LX Music 桌面版 → 设置 → 音源 → 自定义源 → **导入**
3. 在同一页把「接口」选成 **BiliMusic 音源**
4. 回搜索页，用任意内置源（酷我 / 酷狗 / QQ / 网易 / 咪咕）搜歌，点播放

脚本接管了 `kw / kg / tx / wy / mg` 五个源的取流，**用哪个内置源搜都可以**，播放时统一走 B 站。

### 调试

脚本默认静默运行，不弹 DevTools、不打任何日志。排查问题时把脚本里的这一行改成 `true`：

```js
const DEBUG = false   // → true
```

改完重新导入，DevTools 会自动弹出，并输出每一步：

```

[BiliMusic v1.4.0] 收到请求 action=musicUrl source=kw 音质=128k 歌曲=「发如雪」歌手=「周杰伦」时长=04:59
```

### 前置条件

- LX Music 桌面版 **2.12.6** 实测通过（自定义源协议其他版本可能不同）
- 能直连 `api.bilibili.com`（需要匿名指纹 `buvid3`，脚本会自动取）

## 二、为什么它不能"搜歌"

这是本项目最重要的一条结论：**LX 自定义源在协议上只能"接管取流"，不能提供搜索，也不能新增音源类型。**

拆 `app.asar` 里的 `dist/user-api-preload.js` 可以逐条验证：

| 限制 | 证据 |
|---|---|
| `sources` 的 key 只能是 `kw/kg/tx/wy/mg/local` | 源码里是硬编码枚举 |
| 非 `local` 源的 `actions` 只能有 `musicUrl` | 生成的能力只有 `getMusicUrl / getPic / getLyric` |
| 写了 `actions: ['search']` 也会被过滤 | `actions.filter(a => userSource.actions.includes(a))` |
| 搜索永远走内置 `musicSdk` 模块 | 搜索页根本不读 `apiSource` |
| 只能返回一个 URL 字符串，不能附带请求头 | 返回值校验 `^https?:` 且长度 ≤ 2048 |

所以"B 站音源"注定是**影子音源**：列表还是内置源给的，声音是 B 站给的。

市面上流行的「星海」「25 源合并」等脚本，声明的也都是 `['musicUrl','lyric','pic']`——所有人都在做取流器，因为协议只允许做到这一步。

## 三、取流与匹配原理

```mermaid
flowchart LR
  A[搜索框关键词] --> B[LX 内置源搜索]
  B --> C[歌曲列表<br/>musicInfo]
  C --> D[点播放<br/>action=musicUrl]
  D --> E[脚本拼关键词<br/>歌名 + 歌手]
  E --> F[B站 search/type]
  F --> G[打分排序]
  G --> H[三道硬校验]
  H --> I[playurl<br/>html5/durl]
  I --> J[不带 Referer 验流]
  J --> K[返回直链给 LX]
```

### 关键词是脚本重新拼的

LX 传给脚本的是结构化元数据，不是搜索词：

```js
info.musicInfo = { name: '雨爱', singer: [{ name: '杨丞琳' }], interval: '04:20', ... }
```

脚本拼成 `keyword = name + ' ' + singer`，即「雨爱 杨丞琳」。所以搜索框里输入的「女声 伤感」不会传到 B 站；你点的是哪一首，决定去 B 站搜什么。

### 打分规则（决定尝试顺序）

| 规则 | 分数 |
|---|---|
| 标题包含歌名（去标点、转小写后比较） | **+50** |
| 标题包含任一位歌手 | **+20** |
| 时长与 LX 给的一致（差 ≤20s） | **+30** |
| 差 ≤60s | +12 |
| 差 >180s | −25 |
| 标题含 歌词 / 无损 / 高音质 / 纯享 / 完整版 / hifi | +8 |
| 标题含 合集 / 串烧 / 连播 / 精选 / 小时 / 热歌 / 歌单 / 榜单 | −15 |
| 无时长信息时，落在 100–420s | +15 |

满分 108。打分只决定顺序，能不能用还要过下面三关。

### 三道硬校验（决定最终结果）

1. **视频总时长 < 40s → 直接丢弃**（片段、预告、鬼畜切片不可能是完整歌曲）
2. **多 P 合集 → 必须在分 P 标题里定位到这首歌**（分 P 名含歌名 +60、歌名含分 P 名 +40、分 P 时长差 ≤15s +30；总分 <30 就跳过，否则会放成合集第一首）
3. **单 P 但你要的是短歌而视频 >900s → 跳过**（串烧，拆不开）

三关都过，才调 `playurl` 拿 `durl[0].url` + 两条备用地址，再**不带 Referer** 验流。失败就换备用地址，三条都废就退到下一名候选，最多试前 5 个。

结果按 `歌名|歌手|时长` 缓存 90 分钟（B 站地址带 `deadline` 签名，约 2 小时失效）。

### 音质说明

LX 自定义源只能返回一个不带请求头的 URL，而 B 站 CDN 会强校验 Referer。绕开防盗链的唯一通道是 `platform=html5`，拿到的是**音视频整合 mp4**，音轨为 AAC（一般 64kbps）。这是协议边界与防盗链共同决定的，不是脚本参数没调对。

## 四、踩过的坑

按排查顺序，每条都是"看起来正常、实际必挂"的类型。

| 版本 | 问题 | 真相 |
|---|---|---|
| v1.1 | 初始化成功但一切失败 | `inited` 字段名写成 `openDevMode`，LX 只认 **`openDevTools`** |
| v1.2 | 每次 API 调用必抛异常 | LX 的 `lx.request` **已经把 JSON parse 成对象**再放进 `resp.body`；再 `JSON.parse(String(obj))` 得到 `"[object Object]"` → 必挂 |
| v1.2 | `qualitys` 里的 `192k` 被静默过滤 | 合法值只有 `128k / 320k / flac / flac24bit` |
| **v1.3** | **脚本日志全绿，LX 播放全红** | B 站 CDN 强防盗链：无 Referer → 403，酷我/酷狗 Referer → 403，只有 `Referer: https://www.bilibili.com/` → 206。而脚本自检时自己带了 B 站 Referer，**完美地骗过了自己** |
| v1.3.1 | 点播放只响 12 秒 | 打分里歌名 +50 能压过时长 −25，一条「12 秒高能片段」也能夺冠 → 加 `<40s` 直接跳过 |
| v1.4.0 | 日志太吵 | 加 `DEBUG` 开关，默认关闭并删除启动自检 |

关键教训：**自检必须用和真实客户端完全相同的请求条件**。v1.3 之前所有"验流通过 HTTP 206"都是假的，因为它验的不是播放器将要发出的那个请求。

## 五、已知限制

- **不能搜索**。见第二节，这是协议边界，不是实现问题。
- **音质上限 64k**。见第三节「音质说明」，LX 路线拿不到 192k 纯音频。
- **匹配只看标题字符串**，没有音频指纹。翻唱、现场、DJ 版、MV、纯音乐都可能命中；标题与内容不符的视频也会漏过去。
- **歌词与音轨可能对不上**。歌词由 LX 自己从内置源/本地库取（按歌曲 id），音频却来自 B 站，版本可能不同。
- 需要能访问 `api.bilibili.com`；部分网络环境会触发 412 风控。
- B 站地址约 2 小时过期，脚本内缓存 90 分钟；长时间暂停后继续播放可能需要重新取流。
